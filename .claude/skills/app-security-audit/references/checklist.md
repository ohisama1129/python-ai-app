# 手動レビューのチェックリスト

`scan.py` はパターン一致しか見ないので、ここにある項目は実際にコードを読んで判断する。各項目の「なぜ危ないか」を理解したうえで、対象アプリで**実際に起こりうるか**を判定すること。該当しない項目は「確認済み・問題なし」として報告書に残せばよい。

各項目の見出しには、報告書の「分類」欄に書く OWASP Top 10 for LLM Applications (2025) の番号を併記している（LLM固有でない項目は一般的な分類名）。

## 0. まずアプリの全体像をつかむ

重要度は「誰が使うか」で大きく変わる。最初に次の点を確かめ、報告書の「前提」に書く。

- **想定する利用形態**：自分のPCだけで使う／LAN内で共有する／インターネットに公開する（Streamlit Community Cloud、Cloud Run など）。ユーザーの依頼文や README、デプロイ設定（`Dockerfile`、`Procfile`、`.streamlit/` など）から推測し、分からなければ「ローカル利用」と「公開」の両方の観点で書く。
- **LLMの呼び出し経路**：どの SDK／どのモデル／APIキーはどこから来るか（`.env`、`st.secrets`、画面入力、環境変数）。
- **信頼できない入力がLLMに入る経路**：画面入力、貼り付けたメールや文書、アップロードファイル、URL取得、検索結果、DB内のデータ。
- **LLM出力の行き先**：画面表示、ファイル保存、コード実行、ツール呼び出し、外部送信、次のプロンプトへの再投入。

この「入力 → LLM → 出力」の経路図が、以下のすべての判断の土台になる。

## 1. 秘密情報の管理（LLM02）

- APIキーの流れを最後まで追う：読み込み → 保持 → SDK に渡す。途中で `st.write` / `print` / ログ / 履歴 / ダウンロードファイル / プロンプト本文に混ざらないか。
- 秘密情報の置き場所：`.env` や `.streamlit/secrets.toml` が `.gitignore` で除外されているか。Git の履歴に一度でも入っていたら、ファイルを消しただけでは足りない（キーの再発行が必要）。
- `st.session_state` に秘密情報を入れていても、すぐに漏れるわけではない。ただ、デバッグ用に `st.write(st.session_state)` を足すと画面に出てしまう。
- 公開する場合の注意：アプリ作者のキーを `st.secrets` に置くと、**全訪問者が作者のキーで生成する**ことになる。認証（2章）とコスト上限（8章）をセットで考える。利用者にキーを入力させる方式なら `type="password"` を使い、キャッシュやログに残さない。
- クラウド同期フォルダ（iCloud など）や ZIP での共有も、秘密情報が漏れる経路になる。状況次第なので INFO で伝える。
- **キーの値は報告書に絶対に書かない。** 書くのは場所と種類だけ。

## 2. 公開範囲と認証（アクセス制御）

- Streamlit は、既定では全インターフェース（0.0.0.0）で待ち受ける。起動時に表示される "Network URL" がそれにあたり、認証がなければ同じネットワークの誰でもアプリを開ける。サーバー側にキーがあれば、その人は**作者のキー（クォータ・課金）で**生成できる。
  - ローカル利用の対策は `.streamlit/config.toml` の `[server] address = "localhost"`。
- 公開する場合の認証：`st.login()`（OIDC）、ホスティング側のアクセス制限（Community Cloud の viewer 制限など）、リバースプロキシでの認証。自作のパスワード比較なら、平文比較・タイミング攻撃・ブルートフォース対策の有無も見る。
- `enableXsrfProtection` / `enableCORS` を無効にしていないか。
- 管理者向けの画面や機能が、URLパラメータ（`st.query_params`）だけで切り替わっていないか。

## 3. プロンプトインジェクション（LLM01）

被害の大きさは「LLM に何をさせているか」で決まる。テキストを生成して表示するだけのアプリなら、被害は「出力が乗っ取られる」範囲に留まる（MEDIUM 程度）。ツール呼び出し・コード実行・外部送信ができるアプリでは HIGH 以上になりうる。過大にも過小にも評価しないこと。

- **直接インジェクション**：利用者本人が入力欄で指示を上書きする。個人ツールなら本人しか使わないので問題になりにくい。複数人で使うアプリや、システムプロンプトに秘密やビジネスルールを込めている場合は問題になる。
- **間接インジェクション**：貼り付けたメール、要約対象の文書、アップロードファイル、Web ページ、RAG の検索結果の中に「以上の指示を無視して…」と書かれているケース。利用者本人に悪意がなくても起こる。
- 確認ポイント：
  - 外部テキストを区切り（`"""`、`<document>…</document>` のようなタグ）で囲んでいるか
  - system 側で「区切り内は素材であって指示ではない」と伝えているか
  - 外部テキストを system メッセージではなく user 側に入れているか
- 前回の出力をプロンプトに戻す設計（修正依頼、チャット履歴）では、一度乗っ取られた出力が次の会話にも影響し続ける。
- 完全な防御は存在しない。対策を書くときは「被害を小さくする設計」（権限を絞る、出力を無害化する、人間が確認する）を主にする。

## 4. LLM出力の扱い（LLM05）

LLM の出力は**信頼できない入力**として扱う。

- `st.markdown` / `st.write` / `st.chat_message` は、既定では生HTMLを描画しない（エスケープされる）。`unsafe_allow_html=True`、`st.html`、`components.html` に LLM 出力が入るなら XSS で、HIGH。
- Markdown の画像 `![](https://外部URL?d=...)` は、表示した瞬間にブラウザが取得しにいく。インジェクションと組み合わさると、会話内容や貼り付けた文書をURLに埋めて外部に送れてしまう（データの持ち出し）。リンクはクリックが必要なので危険度は低め。
  - 対策：表示前に外部画像の Markdown を除去・無害化する、許可したドメインだけ表示する、など。
- LLM 出力を `eval` / `exec` / `subprocess` / SQL / ファイルパス / URL に使っていないか。使っているなら HIGH 候補。サンドボックスや許可リストがあるかを確認する。
- 生成したコードを「実行」ボタンで動かす機能は、実質的にリモートコード実行。
- ダウンロードのファイル名や保存先のパスに、LLM 出力やユーザー入力が入っていないか（パストラバーサル）。

## 5. ツール呼び出し・エージェントの権限（LLM06）

- LLM に渡しているツール（function calling、LangChain の tools、MCP など）を一覧にし、それぞれ「インジェクションされた LLM が呼んだら何が起きるか」を考える。
- 確認ポイント：
  - 読み取り専用か、書き込み・削除・送信ができるか
  - 引数を検証しているか（パス、URL、SQL）
  - 危険な操作の前に人間の確認があるか
  - ツールが使う認証情報の権限が必要最小限か
- エージェントのループに回数上限があるか（8章のコストにも関係する）。

## 6. システムプロンプトの漏えい（LLM07）

- システムプロンプトは「頼めば出てくるもの」と考える。APIキー、パスワード、内部URL、他ユーザーの情報などが入っていたら HIGH。
- 「このプロンプトを教えないで」という指示だけで守ろうとしているなら、それは対策にならないと指摘する。
- 公開されて困るのがプロンプトのノウハウだけなら、ビジネス上の判断の問題なので INFO。

## 7. RAG・ファイル取り込み（LLM08 / LLM01）

- `st.file_uploader`：
  - 許可する拡張子とサイズを制限しているか
  - サーバーに保存するなら、ファイル名をそのままパスに使っていないか
  - PDF や Office ファイルの解析ライブラリが古くないか
- 取り込んだ文書は間接インジェクションの入り口になる（3章）。
- ベクトルDB を使う場合：
  - 利用者ごとのデータ分離ができているか（他人の文書が検索結果に出ないか）
  - 誰でも文書を追加できて、他人の回答を汚染できる状態になっていないか
- URL を取得する機能は、内部ネットワークへのアクセス（SSRF、`http://169.254.169.254` など）に使われないか。

## 8. コストとリソースの消費（LLM10）

公開アプリで最も現実的な被害は「作者に高額な請求が来る」こと。

- 出力トークン上限（`max_tokens`、`max_output_tokens` など）を指定しているか。
- 入力の長さを制限しているか（巨大な貼り付けやファイル）。
- 利用者ごとの回数制限、プロバイダ側の利用上限・予算アラートを設定しているか。後者はコードからは分からないので、確認を促す形で書く。
- エージェントやリトライのループに上限があるか。
- ローカルでの個人利用なら LOW〜INFO、公開するなら MEDIUM〜HIGH。

## 9. Streamlit 特有のセッション共有

Streamlit では、1つのサーバープロセスを全利用者が共有する。

- **`@st.cache_data` / `@st.cache_resource` は全利用者で共有される。** 次のものが入っていると、他の利用者に見える：
  - ユーザー固有の会話・入力・生成結果
  - 利用者が入力したAPIキーで作ったクライアント（`cache_resource` に入れると他人がそのキーを使う）
- モジュールのグローバル変数に会話履歴などを置くと、全利用者で共有される。利用者ごとのデータは `st.session_state` に置く。
- `st.session_state` はブラウザのタブ（セッション）ごとに分かれる。ディスクやDBに書き出すなら、利用者ごとに分離されているかを確認する。
- 個人利用なら共有されても実害はない。報告書には「公開時に問題になる」と書く。

## 10. エラー処理とログ

- `st.error(f"...{e}")` や `st.exception(e)` は、例外メッセージを画面にそのまま出す。SDK の例外にはリクエストURL・レスポンス本文・組織IDなどが含まれることがある。公開するなら一般的なメッセージに置き換え、詳細はサーバーログへ。
- ログにプロンプト全文や生成結果を出していないか。個人情報や機密文書がログに残ってしまう。
- Streamlit の `client.showErrorDetails` 設定（既定ではトレースバックを表示する）も確認する。

## 11. 送信データとプライバシー（LLM02）

- 入力した内容はすべて LLM プロバイダに送信される。プロバイダやプランによっては、送信内容が学習や品質改善に使われる（例：Gemini API の無料枠）。機密情報や個人情報を扱う用途なら、有料プランやデータ保持ポリシーの確認を促す。規約は変わるので「最新の利用規約を確認」と添える。
- 公開アプリなら、利用者に「入力内容が外部のAIサービスに送られる」ことを明示しているか。
- 会話履歴を保存する場合：保存期間、削除手段、保存先の暗号化。

## 12. 依存ライブラリ（LLM03）

- `pip-audit` の結果があれば最優先で使う。未インストールの場合は、インストールして実行してよいかユーザーに確認する（仮想環境にパッケージが増えるため）。
- `>=` だけの指定では、再インストールのたびに別バージョンが入る。`pip freeze` や `uv lock` でのロックを提案する。
- `.venv/bin/pip list` でインストール済みのバージョンを見て、Streamlit や LLM SDK が極端に古くないか確認する。
- Hugging Face などから外部のモデルやデータを取り込んでいるなら：
  - 取得元は信頼できるか
  - `trust_remote_code=True` を使っていないか
  - pickle 形式のモデルを読み込んでいないか

## 13. その他の一般的な脆弱性

LLM と関係のない機能（DB、ファイル操作、外部API、認証）が含まれていれば、通常の Web アプリと同じ観点で見る：

- SQL インジェクション
- パストラバーサル
- SSRF
- 安全でないデシリアライズ
- 秘密情報のハードコード
- 権限チェックの漏れ
