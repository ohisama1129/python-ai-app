# Streamlit + LLM アプリのセキュリティ診断

Streamlit で作った LLM アプリを診断し、セキュリティレポートを Markdown ファイルとして出力する。

この種のアプリでは、少数のファイルに「APIキー」「誰でも開ける Web 画面」「信頼できない文章を読む LLM」が同居している。現実に起きやすい事故は高度な攻撃ではなく、次のようなもの：

- キーが漏れる、または他人に使われて請求が来る
- 外部の文章に LLM が操られる
- 他の利用者のデータが見えてしまう

**重要度は、アプリの利用形態（自分のPCだけで使うのか、公開するのか）を前提に判断する。** 起こりえないリスクを並べて報告書を水増しすると、本当に直すべき点が埋もれてしまう。読み手はセキュリティの専門家とは限らないので、各指摘には「何が起きるか」を具体的に書く。

## 手順

### 1. 自動スキャン

対象プロジェクトのルートで実行する（仮想環境があればその Python を使う）：

```bash
<python> <このスキルのディレクトリ>/scripts/scan.py <プロジェクトのルート> --audit
```

スキャン内容：

- 秘密情報の直書き（主要な LLM プロバイダのキーの形式）
- `.env` / `secrets.toml` が Git から除外されているか、ファイルの権限
- Streamlit の設定（待ち受けアドレス、XSRF）
- 危険な関数（`unsafe_allow_html`、`eval`、SQL の文字列連結など）
- 使っている LLM SDK、認証やトークン上限の有無
- 依存ライブラリ

結果は**手がかりであって結論ではない**。たとえば `st.markdown` の INFO は、表示している値が LLM 出力かどうかをコードで確かめて初めて意味が決まる。誤検知と判断したものは、報告書の「確認済み・問題なし」に回す。

pip-audit が未インストールと出たら、インストールしてよいかユーザーに聞く（仮想環境にパッケージが増えるため）。断られたら「未実施」と記録して先へ進む。

### 2. 手動レビュー

`references/checklist.md` を読み、0章（アプリの全体像）から順に確認する。まず次の3点を把握すると、各項目の重要度が決まる：

- どこから信頼できない入力が LLM に入るか
- LLM の出力がどこへ行くか
- 想定する利用形態

依頼文に「公開したい」「友達に使わせたい」などがあれば公開を前提に、なければローカルでの個人利用を前提にする。ただし、公開時に重要度が上がる項目は、その旨を書き添える。

チェックリストにない機能（独自の DB、外部 API 連携など）があれば、その機能固有のリスクも見る。

### 3. レポートを出力

`references/report-template.md` の構成に従って書き、プロジェクトのルートに `security-report-YYYY-MM-DD.md` として保存する（ユーザーが保存先を指定していればそちら）。同じ名前のファイルがあれば、上書きせず `-2` などを付ける。

書き方のポイント：

- **検出事項には ID（SEC-01…）を振る。** 修正を依頼するときに「SEC-02 を直して」と言えるようにするため。
- **分類欄には OWASP Top 10 for LLM の番号を書く**（LLM と関係ない問題は「Secrets Management」などの一般的な名前）。チェックリストの各章の見出しに対応表がある。
- **対策はコピーして使えるコードや設定で示す。** 抽象的な助言（「入力を検証しましょう」など）だけで終わらせない。
- **「確認済み・問題なし」の項目も必ず書く。** 何を見たかが分かると、読み手は診断の範囲を信頼できる。
- **「診断の範囲と制約」も必ず書く。** 静的レビューであること、未実施の項目を明記する。

保存したら、チャットには短い要約を返す：

- 保存先のパス
- 重要度別の件数
- 優先して直すべき上位2〜3件
- 「修正しましょうか？」の一言

レポートの全文はチャットに貼らない（ファイルで読めるため）。

### 4. 修正は依頼されてから

診断だけを頼まれたなら、アプリのコードは変更しない。ユーザーが選んだ項目（「SEC-01 と SEC-03 を直して」など）だけを直す。

直したあとは：

- `scan.py` を再実行する
- アプリが起動することを確かめる（`streamlit.testing.v1.AppTest` でヘッドレスに起動できる）
- 対応した項目を、レポートの最後に「対応状況」として追記する

## 守ること

- **秘密情報の値を出力しない。** `.env` や `secrets.toml` を `cat` しない。キー名と、値が入っているかどうかだけを確認する（例：`grep -c '=' .env`、`sed 's/=.*/=<redacted>/' .env`）。レポートやコマンド出力にキーが映ると、それ自体が漏えいになる。報告書のコード片でも、キーはマスクする。
- **実際のキーで攻撃を試さない。** インジェクションの検証で LLM API を呼ぶと、クォータや料金を消費する。試すならユーザーに確認してから。稼働中のアプリへの攻撃も行わない。
